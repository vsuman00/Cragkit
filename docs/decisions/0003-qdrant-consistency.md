# ADR 0003: Qdrant consistency profile QD-r1

This dated decision records the design at acceptance. It does not report current implementation or release completion; use the [current roadmap](../roadmap.md) and [RC1 notes](../releases/V6.md) for that state.

Date: 25 October 2026. Task: V5-01. Status: ACCEPTED as a design specification after the failure walkthrough and independent review; implementation and native acceptance remain later tasks. The [current roadmap](../roadmap.md) owns completion state. The normative scenario model is [QD-r1](../../contracts/QDRANT_V5.md), with [failure fixtures](../../contracts/fixtures/qdrant_consistency.json).

For example, if two source chunks are committed but only one vector write completes, the old generation stays active. The new source and vector records can exist without becoming searchable evidence. A separate publication decision makes the complete generation eligible.

## Decision and authority

Qdrant is a candidate replica. A caller-injected authoritative `SourceStore` owns immutable canonical revisions and chunk spans, current document metadata and grants, authorization revision, tombstones, durable ingestion intents, generation manifests and the active-generation pointer. Its implementation must provide atomic conditional document mutation and durable readback of publication outcomes. These are capability requirements, not new public method signatures. Existing Python and TypeScript APIs and wire schemas are unchanged.

This refines [architecture sections 6-7 and 11-12](../architecture/ARCHITECTURE.md). It preserves the [source-release contract](../../contracts/RETRIEVAL_V1.md), [lifecycle barriers](../../contracts/LIFECYCLE_V1.md), [vector generation rules](../../contracts/VECTOR_GENERATIONS_V2.md) and [execution limits](../../contracts/EXECUTION_V4.md). PostgreSQL remains the reference backend; Qdrant is optional. The application chooses and owns source storage. No second service, PostgreSQL deployment, Python bridge, background worker or model download becomes a core requirement.

Immutable canonical content may reside in caller-owned storage, including payload storage for small text, provided the selected profile proves immutable identity, source digest checks and the independent authoritative mutation/publication guarantees. Ordinary Qdrant payload writes alone do not establish this profile's atomic authority. Missing guarantees require `UnsupportedCapability`; an adapter cannot silently weaken QD-r1.

## Identities and manifest

Every logical reference includes tenant, collection, document, revision, generation and chunk identity. The physical Qdrant point ID must map deterministically and collision-safely to that complete identity and the declared index profile. Logical chunk identity is distinct from a physical point ID; no globally unique document ID or truncated unchecked hash is assumed. Any collision or mismatched payload fails closed. Different generations and vector spaces cannot overwrite one another's points. Qdrant accepts unsigned 64-bit or UUID point IDs; the first native target should use deterministic UUIDs and verify the full logical identity and payload digest before any replacement, avoiding JavaScript integer precision loss. A same-ID upsert replaces the whole point, including omitted named vectors, so retries must supply the complete expected point rather than a partial replacement. [Qdrant points](https://qdrant.tech/documentation/manage-data/points/).

A durable intent binds its idempotency key to the canonical payload digest, expected active pointer, source identity, parser/chunker profiles, dense and sparse identities, required chunk membership and mutation epoch. Reusing the key with changed content, profiles or expected publication intent is rejected. An identical retry resumes that intent; it does not create another active generation or reuse historical provider usage as new measured usage.

Per-document coordination cannot prevent two different documents from racing on a colliding physical UUID. Before any point write, require an atomic authoritative ownership reservation keyed by backend/physical-collection incarnation and point ID, shared by all writers to that collection. It binds the full scoped immutable identity and profile. Repeated identical claims are idempotent; a conflicting claim raises `IntegrityViolation` before replacement. Read the same claim after an uncertain acknowledgment. Separate read-before-upsert checks are insufficient. A SourceStore without this registry capability, or independent authorities without a common registry, cannot share this profile's physical collection. Keep claims through retained content, unresolved writes and intents; reclaim only after verified cleanup and durable fencing of old writers. An empty point read or expired lease does not permit reuse. Retain only ownership metadata under the owner's deletion policy. Recreated collections use a new incarnation and fence old writers/credentials before namespace reuse.

The immutable manifest binds the generation to:

- canonical UTF-8 source digest and immutable locator/revision;
- every expected chunk's exact byte span and excerpt digest;
- the exact expected physical point membership and each point's logical identity, content binding and dense/sparse profile;
- encoder and index configuration, including vector names, dimensions, distance/normalization where applicable, and required payload filter fields;
- the captured document mutation epoch and expected active pointer;
- completed-write evidence and full-set verification state, followed by the authoritative publication outcome.

Counts are useful diagnostics. Equal counts alone cannot distinguish a missing point from an unexpected replacement. Verification must establish exact membership, no duplicates or extra points in the generation namespace, matching payload digests/profiles and validated vectors. A canonical membership digest is usable only when computed over the entire verified set with a declared deterministic serialization. A server count or a single successful batch acknowledgement is insufficient. Content digests cover canonical bytes and membership; they do not require exact round-trip equality of incoming float64 JSON vectors. Validate complete named-vector presence, stored finite values, dimensions and declared profile semantics separately. If a later adapter requires a vector checksum, it must first freeze a cross-runtime float32 binary encoding and byte order; arbitrary floating-point JSON is not a canonical checksum representation.

## Publication barrier

Use one mutation order for each document, with atomic fencing in the authority. Cross-store atomic commit is not assumed. The following stages describe required effects, not an implemented API:

1. Authorize the writer and persist the stable intent and immutable source/chunk manifest in staging. Capture the expected active pointer and mutation epoch. No candidate becomes published.
2. Write generation-isolated points in bounded idempotent batches. Do model work outside authoritative mutation transactions. Do not copy candidate text into a provider request during publication.
3. Confirm completed durable writes according to the selected Qdrant configuration. Resolve unknown write outcomes by inspecting the same operation/intent and exact point identities. Verify the complete manifest set through the read path/configuration required by the profile. An accepted, queued or ambiguously acknowledged operation is not completion evidence.
4. Reauthorize the writer and conditionally publish in one authoritative atomic mutation: require unchanged expected pointer, matching intent/manifest, verified completion, current epoch, current authorization revision and a live non-tombstoned document; then mark the generation published/ready, record the durable intent outcome and switch the active pointer together. No Qdrant write belongs inside this atomic authority operation.
5. Read back the same authoritative intent after a lost publication acknowledgement. If its matching outcome committed, report/reconcile that outcome. If it did not commit and the fence still matches, retry the same conditional operation within budget. If another publication or security mutation won, stop with conflict; do not restore an old pointer or overwrite the newer outcome.

Publication verification and CAS require a mutation fence that covers all participants. A repair worker cannot alter a verified generation between validation and publication. Published vector/content/profile/membership fields are immutable; changes to those fields require a new generation. ACL/filter replica fields and their mutation epoch are separately mutable and excluded from the immutable content digest. Lease expiry alone is insufficient: a stale worker must be fenced out of subsequent writes. The first profile requires a caller-owned document mutation coordinator that serializes ingestion, ACL replication, repair and cleanup for each complete tenant/collection/document key and restricts direct point writes to those participants. Ownership transfers must drain already dispatched operations and resolve ambiguous acknowledgements before the successor can replace or delete points. A process crash leaves ownership blocked until that reconciliation completes; an expired lease is not permission to overlap writers. This is an explicit injected deployment capability, not a required core service or an assumed Qdrant per-point CAS. Without this exclusion/draining mechanism, reject QD-r1 compatibility. Arbitrary out-of-band administrator mutation is outside the library trust boundary and requires operational detection; QD-r1 does not claim a perpetual cross-store snapshot against it.

Completed writes and a successful authoritative CAS do not make a distributed read infallible. Every candidate is checked against authoritative published membership before source use; a missing/corrupt replica after publication is an operational/integrity failure, never fabricated evidence. A configuration that cannot establish the required write durability/read visibility must fail capability negotiation. Qdrant replication, write ordering, acknowledgement and read consistency must be selected and tested explicitly by V5-02/V5-04. No distributed transaction or universal durability guarantee is inferred from a request option. Qdrant distinguishes accepted acknowledgements from completed writes (`wait=true`); read consistency, write consistency and write ordering are separate controls. [Qdrant points](https://qdrant.tech/documentation/manage-data/points/), [consistency guarantees](https://qdrant.tech/documentation/scaling/consistency-guarantees/). The first reference target is a single-node profile; distributed deployments remain unsupported until their exact configuration passes separate conformance. Even that reference target requires explicit durability and readback acceptance.

## Search, source release and ACL synchronization

Bind trusted tenant, collection, grants, authorization revision, required filters and limits outside agent-editable input. Apply tenant, collection and all required supported filter predicates in every dense, sparse and identifier branch before candidate selection. A filter that cannot be represented is unsupported. Bounded expansion may address underfill with exactly the same predicates; permission broadening is forbidden.

Qdrant ACL/filter payloads are replicas. Every candidate carries the replica authorization/mutation revision, but that revision never grants access. Before accepting a new search candidate, check its complete identity/profile and current active published generation against the authority. Immediately before source text reaches any reranker or other external provider, freshly resolve immutable canonical bytes and verify current scope, grants, metadata filters, authorization revision, tombstone, published manifest membership, source digest and UTF-8 span/excerpt digest. Query-only model disclosure still requires the configured provider policy and ledger limits.

Release source-store leases before model work. After model work, freshly authorize and verify source release again before packing/final delivery. A candidate selected before an active-pointer change may still resolve a retained, previously published immutable generation under current authorization and filters, with `stale_evidence`, as the existing source contract allows. Staging, aborted or never-published generations cannot use this retained-generation exception. Mixed revisions, unchecked Qdrant excerpts and unverified provider-returned IDs are forbidden.

Commit ACL revocations, metadata restrictions and tombstones in the authority first, atomically advancing the mutation epoch and current authorization state. Old vectors may remain, but fresh authoritative checks deny their text. Replicate the updated predicates afterward through fenced bounded jobs. Grant additions may leave old replica filters too restrictive until synchronization; report/handle underfill without dropping predicates or claiming complete coverage. Delayed ACL updates cannot overwrite a newer ACL state. Security state is never restored by content rollback, replay, repair or generation switching. A complete-point replay cannot restore ACL/filter payload fields from its old staging snapshot: under the document coordinator it obtains the current authoritative replica state and settles earlier writes before replacement, or uses a supported operation that leaves those mutable fields untouched. The same coordination prevents a late old ACL write from overwriting a newer replica epoch.

If current authorization/source authority is unavailable, fail closed with the applicable existing typed operational error, such as `ProviderUnavailable` or `DeadlineExceeded`. A known missing, deleted or deauthorized source is unavailable evidence under the existing source contract; a service outage is not an empty search. A revocation that commits after a successful authorization snapshot cannot retract bytes already disclosed. The final check narrows this race; it does not promise atomic revocation across a remote provider request or application delivery.

## Delete, repair and every partial outcome

Deletion first commits the authoritative tombstone and advances the mutation epoch, denying fresh retrieval regardless of leftover points. Retention and authorized purge then remove derived points and sources in bounded steps. Preserve a minimal authoritative deletion barrier sufficient to fence old intents; do not resurrect a purged document through retry. A Qdrant purge must target exact tenant/collection/document/generation identities, never an unscoped collection-wide delete. Caller policy owns source retention and external logs/caches. Fencing stops future dispatch but cannot cancel a Qdrant write already dispatched: a late point upsert may land after tombstoning or a purge batch. Keep the durable purge intent pending until relevant writers drain, ambiguous outcomes resolve and an exact scoped recheck confirms cleanup; repeat bounded cleanup as needed. This protocol guarantees the authoritative disclosure barrier, not a physically atomic cross-store delete.

Repair reads the durable intent, current pointer, epoch and tombstone before acting and before every conditional mutation. It resumes only missing or uncertain effects for the same intent and immutable identities. A completed matching intent is reconciled without another publication. Superseded/denied intents are fenced and cannot become active. Cleanup must prove generation ownership and that it is neither active nor a retained published generation protected by policy; a concurrent publication/delete/repair wins through the same fence. Never delete a newer generation to undo an older job.

| Interrupted boundary | Visible state and required recovery |
| --- | --- |
| QD-W01/W02: Intent/source write fails before commit | Existing active generation stays visible; reconcile ambiguous authority writes before creating/reusing an intent. |
| QD-W03/W04: Source/manifest commits; no points or partial batch | Staging remains invisible; resume exact missing membership under the same intent. |
| QD-W04: Point acknowledgement is lost or operation only accepted | Completion is unknown; inspect exact effects and operation state, then bounded same-identity retry; no publication yet. |
| QD-W05/W06: All points exist; durable completion or verification record is absent | Staging remains invisible; establish completion and verify the full set before CAS. |
| QD-W05: Verification finds a missing/extra/mismatched point | Keep previous active generation; reject corruption or repair only fenced owned staging records, then repeat full verification. |
| QD-W07/W09: Prepared verification exists; epoch/pointer changes before CAS | CAS fails; preserve the winner and current security state; no stale publication. |
| QD-W07: Atomic ready/pointer/outcome transaction aborts | Old pointer remains; matching staging intent can retry only if all current fences still hold. |
| QD-W08: Atomic publication acknowledgement is lost | Read durable intent outcome; a committed matching publication remains published, never compensated by security rollback. |
| QD-W10: Physical point claim conflicts or acknowledgement is lost | Reconcile the atomic shared claim; a different document cannot overwrite the reserved point, even with a colliding UUID. |
| QD-A01/D01: ACL or tombstone commits; replica update/delete fails | Authoritative denial remains effective; bounded fenced replication/cleanup may resume. |
| QD-A02: Replica ACL mutation acknowledgement is lost or arrives late | Reconcile current epoch and exact payload; stale workers cannot replace newer ACL state. |
| QD-D02: Tombstone commits; source/vector purge partly succeeds | Retrieval stays denied; retain deletion barrier and resume exact authorized cleanup. |
| QD-D03: Repair races newer publication or deletion | Fence the stale worker; preserve newer pointers, tombstones and retained content. |
| QD-R01/R02/R03: Published points or source authority later fail verification | Do not release unchecked bytes or infer no relevant evidence; surface operational/integrity failure and repair under current authority. |

## Sparse profiles, limits and acceptance boundary

Sparse capability requires an explicitly configured encoder identity, version/artifact or provider identity, tokenization/preprocessing, query/document transformations, vocabulary/index mapping, value semantics and any corpus-dependent weighting/statistics epoch. Validate sparse indexes/values and query/document compatibility. A corpus-dependent encoder change requires a new compatible generation/profile. Do not label sparse vectors BM25 unless the declared implementation actually implements the stated BM25 profile. Native PostgreSQL FTS remains `native_fts.v1`; neither dense vectors nor a Qdrant sparse field makes it BM25.

QD-r1 selects no sparse model, paid provider or model assets. Dense-only deployment may declare sparse/hybrid unsupported; explicit degraded fallback retains existing capability/status rules. Construction/import never downloads a model, opens a network connection, discovers credentials or provisions storage. Native Python and Node clients remain optional and caller-owned.

Search, source verification, provider calls, writes, reconciliation and repair consume their operation's shared deadline and cancellation budget. Set finite batch size, candidate/point enumeration, source-byte, attempt, call and concurrency bounds before dispatch. Full-set verification cannot silently truncate and still publish; exceeding bounds leaves staging or fails explicitly. Retry accounting includes attempted/uncertain calls and does not claim unknown cost is zero. Cancellation stops subsequent dispatch, closes task-owned resources within bounded cleanup and leaves durable staging recoverable. Borrowed clients/pools remain caller-owned. No service or recurring repair loop starts implicitly.

V5-01 freezes this design and walkthrough only. V5-02 must select exact supported client/server versions and consistency settings, build native scoped candidates and validate capability/filter/profile behavior. V5-03 must verify stale-ACL/provider-disclosure and final-release races. V5-04 must prove write-boundary recovery, full-set completeness, concurrent fencing, ambiguous acknowledgements and deletion in an isolated backend. V5-07 owns cross-runtime/backend conformance. Live-provider quality, performance, production operations and package publication need their own evidence.

Learning exercise: start with an old published generation and a new two-point staging generation. Lose the acknowledgement for the second point, then commit a tombstone. Explain why finding both points afterward still does not authorize publication or provider disclosure.
