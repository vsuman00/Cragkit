## Behavior

[DN-r1](../../../contracts/DENSE_V2.md) freezes the E-r1 single-vector input, exact profile and score semantics. The candidate carries cosine distance in [0,2], lower-is-better direction, metric identity, embedding profile and immutable source keys/spans/digest. For example, the same direction ranks before an orthogonal vector and then the opposite direction. Equal scores use stable document/revision/ordinal/chunk ordering. This is geometry, not relevance confidence.

The [canonical query](../../../storage/postgres/queries/dense_candidates.sql) materializes the authorized eligible set before ranking and LIMIT. Full composite joins bind vectors to chunks, revisions and active ready generations. Tenant, collection, principal/grants, authorization revision, tombstones, exact vector/generation profile and required filters remain mandatory. The effective limit is bounded by both the caller and request. No approximate index is added; an exact scan still grows with the authorized filtered corpus and has no measured large-corpus performance guarantee.

Dense selection runs inside the existing read-only repeatable-read transaction. Query embedding happens before that transaction under caller-owned authorization/disclosure and usage accounting; the dense method makes no provider call. Capability, setup history and exact registry identity are checked only when dense is selected, so lexical-only reads remain independent. Malformed batch/candidate data, operational failure and missing capability fail explicitly. No fallback converts them into empty evidence.

Dense metadata is validated before projection into the unchanged base source identity. Fresh source fetch still rechecks current scope, grants, filters, tombstones, revision, exact UTF-8 bytes and digests. Authorized immutable retained generations can be released as stale after publication. Neither a score nor a declared profile grants source access.
