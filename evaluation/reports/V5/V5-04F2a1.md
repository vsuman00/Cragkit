# V5-04F2a1: Manager authority admission

This child adds three private writer primitives in Python and Node: bounded manager metadata snapshots, original-fence publication admission and exact dispatch outcome lookup. Public transport/manager implementation remains F2a2; worker-channel and full publication/crash acceptance remain F2b/F3/G/H. Full V5 is incomplete.

For example, if another publisher replaces G1 with G2 while an old intent waits, admission records conflict and leaves G2 and its owner unchanged. A caller's stale authorization revision instead raises UnauthorizedScope without poisoning a valid intent.

## Behavior

Snapshots expose only closed intent/current-document/backend/owner metadata, bounded journal sequence and document-wide unresolved-work state. They require current scope, preserve tenant isolation and never authorize an HTTP operation or SQL settlement. Dispatch lookup verifies the raw request hash, operation, exact physical membership and claim ownership before returning immutable metadata without request bytes.

Admission refreshes the intent and current document after the backend/owner/document lock sequence. It records original security denial or pointer conflict before takeover, preserves historical terminal outcomes and never rebases an intent. Valid new ownership requires open admission, no unresolved document dispatch and a fully reconstructed immutable stage graph.

A narrowly detected failure at actual COMMIT triggers fresh same-identity confirmation, then at most one same-context admission retry if still unresolved. It discards the uncertain connection. Body failures and native cancellation do not enter that reconciliation route. A metadata result remains separate from write authorization or proof of HTTP completion.

## Integration findings and limits

Focused Python checks first found a fixture assertion matching role-catalog SQL instead of the owner lock, and exception copying that prevented a simulated body failure from reaching BEGIN. Corrected fixtures now exercise the intended rollback and lock ordering. Source review also found a stale intent read after an owner-lock wait in Node; refreshing it preserves a same-intent completed outcome. Both runtimes use fresh confirmation before considering a lost-commit retry.

No schema, source-reader, supervisor/recovery, profile codec, dependency lock, sealed input or user audit draft changed. No hosted mutation, provider call, installation, model download, registry release or persistent service is part of this acceptance. Practice remains unassessed: explain why a lost COMMIT response does not mean the transaction rolled back, and why that still cannot prove an HTTP write completed.
