## Implemented behavior

The optional publication modules export `ManagedQdrantPublicationWorkerHost(supervisor, authorize_write)` and the owned diagnostic handle. The application stages first, then calls `host.publish(job, ledger, deadline/options)`. The child runs the actual native pool, writer, publication transport, verifier and manager. Python launches Python with an isolated fixed module entry; Node launches its fixed package entry. No required Python service, arbitrary executor, model runtime, reconnect or automatic supervisor takeover was added.

The job contains exactly writer-pool configuration, complete QC configuration, trusted scope, publish reference and limits. The parent reserves one logical attempt on the original ledger and controls the deadline. The child receives a local budget mirror. Storage makes no model calls and charges no candidate reservations.

A private inherited framed channel carries bounded control metadata. Original native objects, attempts, channels and owned processes remain in private registries. Keys are delivered once per attempt and reused for direct child HTTP. The parent keeps the actual supervisor capabilities; readback receipts stay local to the child. Asynchronous receipt validation checks current parent authority. Null recovery is accepted only for the registered worker controller; existing E2 proof boundaries remain actual-supervisor-only.

During final publication SQL the parent holds its real supervisor session. EOF, cancellation or timeout requires child reaping and callback drain before exclusion is released. Failed cleanup retains poisoned ownership and refuses new work. Constructors/imports are inert, and host close preserves the borrowed supervisor. [The guide](../../../docs/qdrant-publication.md#running-publication-in-an-owned-worker) gives the public usage and ownership rules.
