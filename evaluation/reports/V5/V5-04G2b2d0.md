# V5-04G2b2d0: Separate-connection guard counterexample

Status: COMPLETE for the native necessity gate. The candidate two-connection guard is rejected. The same-transaction SQL guard and security settlement are not implemented.

For example, connection A locks the current document while connection B submits settlement COMMIT. If A disconnects, another writer can change authorization before B finishes. Keeping A's callback alive cannot keep its lost database lock alive.

The actual disposable PostgreSQL 17 test passed eight checks. A native writer staged a two-member generation, admitted its owner and reserved/dispatched/marked an unknown upsert with explicit synthetic metadata. Authority-only security committed revision two and the old stage became denied. The restricted supervisor advanced the blocked backend and same owner to epoch two, then the separate restricted writer locked and checked the exact current document tuple.

The supervisor selected a synthetic retired-journal completion and submitted actual COMMIT. A deferred constraint trigger on a separate fixture-only table paused that COMMIT at an administrative advisory lock. `pg_stat_activity` and `pg_locks` confirmed the actual COMMIT/advisory wait. The test physically closed only the writer connection and confirmed its backend ended while supervisor COMMIT still waited. A sequential replacement native writer then committed revision three with empty ACL arrays and changed metadata. The full new authority tuple was durable before the barrier was released. After release, both the newer authority and the older synthetic journal settlement were durable.

A separate control retained a writer document lock while a second native writer attempted revision four. The fixture observed that writer waiting, with the actual retained guard PID in `pg_blocking_pids`, then released the guard and required the complete new authority to commit. This distinguishes lock behavior from a timing-only delay. The source, generation, member, claim, replay and already-denied stage history snapshot remained unchanged.

The barrier schema stayed outside `cragkit_qdrant`, so production catalog admission remained active. Its transactional setup gave only the exact disposable supervisor LOGIN barrier INSERT/USAGE. The definer trigger had a fixed owned advisory key, fixed `pg_catalog` search path and no PUBLIC execution. Production capability grants and all three migration files were unchanged. Only the owned committed fixture namespace was dropped. The harness used at most two restricted runtime clients plus one administrative observer, with sequential replacement and a six-slot PostgreSQL fixture.
