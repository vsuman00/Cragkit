# V5-04H: Tombstone during repair

State: COMPLETE for exact fault ID `tombstone_during_repair` only. V5-04H and V5 remain open.

For example, a repair can start writing a successor generation while a user deletes the document. The tombstone must commit without waiting for the replica write. A late write must not publish the successor or restore source access.

Both native consumers publish a base generation, stage its successor, and transfer the settled document owner to that successor through the writer's normal admission path. They then start the real `manager.repair` operation and hold its full-point PUT after durable dispatch. An independent security manager commits an irreversible auth-2 tombstone while that request is held. Retained and fresh source reads deny provider and final release with no source bytes. The purge remains pending, preserving the active pointer and point claims while the old dispatch is unresolved.

The held request reaches Qdrant and returns HTTP 200. The harness withholds the client acknowledgment, leaving an `unknown` journal entry. The repair fails without publishing its successor. The real managed purge path then recovers, fences the old credential, settles the journal, and checks all four document point IDs and a scoped scroll twice before recording purge completion. Repeated final reads show no document points. Exact payload/vector readback and source access for an unrelated document remain intact. No model provider ran.
