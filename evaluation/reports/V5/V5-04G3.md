# G3 managed purge acceptance

The Python and TypeScript publication managers now implement tombstone-bound
managed purge under [QP-r1](../../../contracts/QDRANT_PURGE_V5.md). The
supported native single-node G3 scope passed its final fault checks in both
runtimes. The earlier checkpoint and its limits remain recorded below.

For example, if Qdrant completes a DELETE but its reply is lost, the manager
keeps that dispatch uncertain. An explicit retry physically refences the old
credential before it can settle the journal or erase managed source bodies.
An empty read alone cannot authorize erasure.

The implementation binds the exact committed tombstone, current trusted scope,
full immutable generation inventory and explicit retention policy. It journals
bounded exact-ID deletes, obtains authenticated absence, and invokes the
restricted profile-5 erasure function in the same guarded writer transaction
that records completion. Claims, identities, digests and original byte counts
remain; canonical source, excerpts, vector replays and request bodies become
NULL with irreversible markers. This is managed logical erasure. It makes no
claim about backups, WAL or forensic disk erasure.

Completed retries use retained metadata without loading erased bodies or
repeating HTTP or DML. Lost erasure-COMMIT replies are resolved by a fresh
read-only comparison of the exact retained graph. Purge receipts, projections
and dispatch authorizations are private nominal capabilities; copies or JSON
cannot authorize work. Existing G2 settlement remains restricted to PUTs.

The native scenarios cover published and retained generations, an actual old
completed PUT with its reply withheld, exact deletes, a lost completed DELETE
reply followed by credential refencing, interrupted purge-owner handoff,
forged receipts, erasure rollback after the real function executes, actual

metadata-only retries after a later authorization change, unknown extra point
refusal and foreign-tenant refusal. Restricted source reads and retained source
bindings return unavailable after tombstoning and after managed erasure.

The independent SQL observer runs after runtime clients close. It compares
original revision, member, vector and claim metadata against the fixture and
checks all managed body columns, original byte counts, erasure records,
terminal flags and document barriers. The unknown-extra document retains its
bodies and incomplete flags. Successful task-owned fixtures are removed only
after server, pool, process and listener cleanup.

Native integration exposed a genuine Python lock conflict: the purge validator
requested a document lock already held by its supervisor guard. It now reads
without taking that competing lock and compares the current tuple with the
actual guard binding, matching the accepted G2 pattern. A native SQL spy
rejects that competing lock immediately. Other corrections were confined to
fixture deadlines, semantic comparison of nominal vector contents, actual
schema column names, pre-tombstone scope and typed cancellation expectations.
No migration, role, grant, dependency or security predicate was weakened.

Both final traces also cancel the real public caller after a genuine absence
receipt reaches finalization. An event-gated completion callback stays live
after cancellation. Competing raw admission, recovery and close are refused;
erasure never runs, and the callback drains before a successful explicit retry.
That retry repeats neither DELETE nor credential rotation. The Node fixture's
additional reinitialization probe was removed because failed initialization
invalidates readiness; changing that behavior is outside this cancellation test.
