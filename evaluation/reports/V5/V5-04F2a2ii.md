# V5-04F2a2ii: Public native stage and publish

The optional native Python and Node modules now implement the public managed stage/publish path. They use explicit borrowed authority, transport and supervisor dependencies, journal exact writes, validate actual completed acknowledgments, verify full readback and publish through the original SQL fences. [API guide](../../../docs/qdrant-publication.md).

This completes F2a2's in-process stage/publish scope. The worker channel, actual process-kill matrix, cross-epoch repair attestations, security convergence, purge and remaining V5 tasks are still pending. This is not a full QD-r1 or production-readiness claim.

## Behavior and ownership

`PostgresQdrantPublicationAuthority(writer, recovery)` preserves the original writer/recovery/verifier graph. `ManagedQdrantPublicationTransport(supervisor)` holds the same actual supervisor. The five-argument manager performs no constructor/import I/O. Applications open their pools and initialize the supervisor explicitly; the manager never discovers privileged resources or applies migrations.

Stage commits immutable source and original vectors without a Qdrant mutation. Publish reserves bounded exact batches, sends each once, requires a private actual completed acknowledgment, settles the same journal and obtains a private full-readback receipt. One logical ledger attempt covers each public operation; library storage work charges no model calls or candidates. Results expose nine closed metadata fields and no owner, key, source text or request body.

The final supervisor session excludes lifecycle changes and competing recovery through fresh authorization, validation and SQL finalization. Callbacks run outside SQL. A matching completed retry remains historical and never restores old ACLs or replaces the current pointer.

A same-epoch prepared retry reads original preparation and selected settled-dispatch metadata, then performs fresh locked admission and full readback under the same binding. It requires the original witness digest, sends no replacement upsert and does not replace preparation. Metadata lookup is not ownership proof: current pending work and authority are rechecked before admission.

## Findings corrected

Review found a real Python cancellation bug: a callback suppressing cancellation could return before the original deadline and allow an orphaned operation to continue. Cancellation now remains latched across every business await and before later SQL/HTTP. Two regressions hold such callbacks beyond the cleanup allowance, return before the original deadline and verify that admission/publication never resumes. The finalization session stays held until actual work unwinds. The independent source review found no remaining concrete issue in its scoped ACK, finalization and prepared-retry review; this is not a universal security guarantee.

Integration also corrected Python import/types, strict acknowledgment-result parity, the persistent dispatch-limit error, immediate handling of terminal preparation outcomes, and document-wide pending checks. A Node SQL double ignored point-ID predicates and returned the first claim for the second member; its predicate handling and distinct-claim assertion were corrected without weakening production integrity checks.

The first Python native fixture omitted explicitly opening its borrowed pools and tried to close a verifier without that runtime interface. Fixture setup/cleanup now follows the actual APIs. The failed private directory was removed only after independent native listener absence. Successful fixtures verified shutdown and removed their own storage.

## Limits and next work

The run used one test process, serial native suites and at most two database clients after setup administration closed. Final resource snapshot: 34 GiB available disk and 54 percent system memory free. No task-owned PostgreSQL or Qdrant listener remains. No hosted mutation, provider call, model installation/download or registry publication occurred. Built-package installation and V5 exit remain later tasks.

Cross-epoch prepared repair requires G0's additive append-only attestation evolution; worker finalization needs a parent-owned session equivalent. Neither is implemented by accepting copied proof fields or changing the old preparation. Learning practice remains unassessed: explain why a completed HTTP write can require recovery when its acknowledgment is lost, while a lost SQL acknowledgment can be resolved without sending that write again.
