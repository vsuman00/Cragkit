# V5-04G0: Current-epoch preparation attestations

Status: COMPLETE for G0. This report covers the additive schema and private native attestation path. Public repair, replica convergence, purge and the complete V5 fault matrix remain separate tasks.

A generation prepared in epoch 1 cannot publish merely because a recovery controller starts epoch 2. The original preparation stays immutable. A fresh ordinary readback receipt, admitted under the actual controller's finalization session, can append an attestation for the exact current owner and epoch. Publication then uses that exact tuple and the original expected pointer. It never selects the newest row by timestamp or creates a replacement generation.

## Changes and security boundaries

Migration `0003_preparation_attestations.sql` adds an append-only, forced-RLS table and extends the publication assertion. Existing migrations 0001 and 0002 remain byte-for-byte unchanged. The new migration checksum is `8c6791cd0fd65ff09758c068ebc90a895a4ac21d9713512486d3daf9cb7c8433`; its captured catalog fingerprint is `7ffd3b585b1fe32bc3476a3dc4390b022f5dcfd6c5ed186c9964fec4ffd72848`.

Source readers explicitly support the three known schema profiles. Writers and recovery support the original publication profile and the new attestation profile with separate literal permission maps. Initialization does not apply migrations. Unknown or extra migration history, changed checksums/catalogs and unsafe grants fail closed. Every writer lease rechecks permissions; the new capability allows only SELECT and INSERT on attestations.

Private receipt admission checks the original registered verifier, writer and controller before and after asynchronous validation. The finalization helper must have acquired the real supervisor or worker session. Python additionally requires the same task; Node rejects inherited work after the enclosing lifetime ends. Extended deadlines, missing original cancellation signals, copied receipts and stale attempts cannot supply attestation authority. These guards do not mint physical recovery proofs.

Attestation insertion reconstructs the immutable graph, checks current security and pointer fences, and compares the complete row on retry. Only a lost COMMIT acknowledgment enters same-key reconciliation; an operational error in the transaction body cannot trigger blind replay. Publication keeps the previous active generation until its final transaction succeeds.

## Evidence

- Schema: 27 focused tests and 18 actual PostgreSQL checks passed. The SQL probes use synthetic metadata; they do not establish physical readback.
- Local runtime validation: 2,318 Python/tool tests, 1,181 Node tests, strict TypeScript build and mypy over 46 files passed. A later focused run rechecked the Python early terminal-state guard.
- Native attestation: ten cases per runtime passed against PostgreSQL 17.11 and pinned Qdrant 1.20.0. They exercise actual recovery, owner advancement, reopening, fresh F1 readback, lost real COMMIT acknowledgment, same-row retry, contradictory verification binding, copied/stale receipt denial, preserved original preparation and active generation, same-intent publication and security-change denial.
- Native permission predicates: nine probes per disposable server passed for both runtime SQL predicates, including extra attestation UPDATE grants on the login and fixed capability. Grants were restored before business acceptance.
- Historical source/publication compatibility: 16 native cases passed on the original two-migration publication profile. The three-migration profile passed the same 16 source cases with exact cross-runtime observation hashes. The actual worker regression passed 18 cases, including kill, pause, EOF and finalization cleanup.

Machine artifacts are under `artifacts/V5/V5-04G0/`: `schema-native-04`, `native-final`, local test logs and regression directories. They remain local and contain no committed credentials. Native results assert each runtime's behavior; they do not claim equality of random owner identifiers or provider quality.

The first native run exposed an incorrect test assertion: manager intent metadata does not include `intent_id`. The assertion now checks the actual attestation intent ID and published generation. A Node regression fixture initially referenced the wrong in-memory table name. Both failures were corrected in tests without relaxing product checks. Independent static review also found a Python ordering error that could attempt a terminal published-to-conflict transition; the early prepared-state check and regression address it.

## Reproduction and limits

Use the frozen project environment and commands in [development.md](../../../docs/development.md). The native parent is `tools/check_qdrant_attestation.py`; pass explicit local PostgreSQL/Qdrant paths, the pinned binary checksum, `--allow-local-processes` and a fresh artifact directory. Routine unit tests use fake providers. Native checks use synthetic vectors and actual storage, with one language at a time and at most two database clients. No paid provider call, model install, hosted mutation or package release is part of this task.

The security-change case allows explicit authorization refusal or a durable denied outcome and requires the prior active pointer to survive. This is not evidence of completed ACL replica convergence. An attestation does not settle an unknown dispatch or reopen a blocked backend. Full repair and process-death/purge acceptance remain required before V5-04 and V5 can complete.

All task-owned fixtures/listeners stopped. Failed disposable server storage was removed after process absence checks; content-free failure locations were retained. The resource snapshot showed 37 GiB disk available and 57 percent system memory free. These are observations, not capacity guarantees. The three user-owned audit reports, old migration bytes and all 16 sealed evaluation inputs remain unchanged.
