## Implemented profile

Both internal native modules provide a caller-owned `ManagedQdrantSupervisor`, explicit provisioning, opaque attempt and physical recovery capabilities, immutable credential transports, ordinary worker credential delivery through an explicit trusted callback, repeated physical fencing under the same recovery identity, and bounded shutdown.

This reference profile supports the pinned Qdrant 1.20.0 macOS arm64 binary, private newly owned directories, one loopback listener, disabled clustering and one replica/write consistency. Binary checksum and actual owned-child listener checks precede credential-bearing HTTP. Initialization does not create collections implicitly: a caller's provisioning callback creates the registered collections and owned control sentinel; its return value supplies no proof. The controller independently checks configuration, sentinel ownership/readback and explicit `prevent_unoptimized=false`.

An existing nonempty controller directory is never adopted. Supervisor restart or crash takeover is unsupported, including automatic stale-lock removal. The application keeps this controller alive across writer lifetimes. Recovery within that surviving controller preserves the same storage identity and observes the owned process exit before key rotation and restart. Storage remains after controller shutdown. These boundaries are intentional and do not establish a hosted or general production profile.

Recovery retires ordinary admission. The new key is restricted to recovery handles and cannot be delivered to a worker callback. Physical proof metadata cannot be copied into a valid capability. Repeating recovery fences again with a fresh credential generation without allocating a different durable recovery epoch. E1 has no ordinary-reopen API; E2 must add a private handoff after actual durable settlement.

## Native finding and corrections

The first real Python runs failed closed during old-key verification. A diagnostic wrapper retained actual HTTP behavior and recorded four successful mutations followed by HTTP 401 for the retired key. The design's 403 requirement was incorrect: pinned Qdrant maps invalid credentials to `Unauthorized`; a recognized credential lacking permission may receive 403. The contract, both implementations and both native consumers now require exactly 401 for this retired invalid key. Normal transports classify either 401 or 403 as authorization failure. [Credential validation](https://github.com/qdrant/qdrant/blob/v1.20.0/src/common/auth/mod.rs), [HTTP mapping](https://github.com/qdrant/qdrant/blob/v1.20.0/src/actix/auth.rs).

Initial checks also found a missing Python field annotation and a Node test cleanup call that masked failures; both were corrected and rerun. Pair assembly added Node binary identity and initialization-failure cleanup checks. Independent review found Python admission poisoning on invalid recovery epochs, retained closed-handle exhaustion and missing known-dead-child guards; root corrected these and added regressions before the final native and full-suite runs.
