# V1-05: Python staged ingestion

Status: COMPLETE, 21 October 2026. Explicit Python ingestion publishes a complete lexical generation in one PostgreSQL transaction. V1 as a whole remains in progress.

## Behavior and boundaries

`cragkit.ingestion.PostgresIndexer` requires a pool resource and a constructor-bound asynchronous `authorize_write(scope, collection, document_id)` callback. Only an exact `True` authorizes work. The callback runs for every call, including replay, before parsing or leasing. It shares the absolute deadline and cancellation. The consuming application authenticates trusted scope and implements write policy; read grants do not imply write permission. Database RLS remains a separate boundary. This is an internal V1 API, not a newly exposed agent tool.

Inputs include text/UTF-8 bytes, collection/document/intent IDs, source locator, trusted scope, absolute loop deadline, optional metadata, canonical options and expected active generation. Identity and metadata boundaries reject NUL and malformed Unicode. Metadata is bounded native JSON, snapshotted before awaiting authorization; caller canonical options are copied. Canonicalization and optional caller token counting happen outside the database lease. No model, embedding or migration runs here.

Inside the transaction, the indexer validates the actual LOGIN role, RLS, schema/history and collection profile, binds local scope, and obtains parameterized transaction advisory locks for intent then document. It inserts one immutable revision, staging generation, bounded chunk batch and native FTS rows. Counts must agree before a ready generation and active pointer publish together. An existing document requires an explicit matching expected generation and current authorization revision; tombstones reject writes. New documents receive only the principal grant. Existing ACL rows are preserved; arbitrary scope grant IDs never become new ACL rows.

The writer rejects owner/admin/bypass/schema-creator roles and effective DELETE/TRUNCATE privileges. The hosted fixture grants SELECT/INSERT/UPDATE without DELETE or TRUNCATE. Administrative cleanup uses separate credentials. Every SQL data value is parameterized. No permanent application policy or login is installed.

Same intent and identical payload returns the original receipt without new rows or republishing an older generation. Changed payload or document under that collection/tenant intent fails. A prepublication callback failure, cancellation or timeout rolls back all staging rows, retaining the prior active generation. Nonidle cleanup and uncertain commit connections are discarded within a bounded cleanup budget. A lost COMMIT acknowledgement can mean the server committed even when the call reports an operational error; retry the same intent to resolve that ambiguity. The tests do not claim cancellation can undo an already committed transaction.

## Deterministic identifiers

Compact UTF-8 JSON uses no ASCII escaping or optional whitespace. Hashes are SHA-256. Shared `contracts/fixtures/ingestion.json` contains eight independent metadata cases. Metadata hashes use a bounded TLV encoding so Python/JavaScript number formatting does not change identity: null `n`, false `f`, true `t`; numbers `d` plus IEEE-754 big-endian binary64 with negative zero normalized; strings `s` plus unsigned 32-bit big-endian UTF-8 length and bytes; arrays `a` plus count and child encodings; objects `o` plus count and UTF-8-byte-sorted encoded key/value pairs. Maximum encoding is 65,536 bytes; native JSON limits depth/nodes and finite safe numbers.

Payload identity includes tenant, collection, document, intent, locator, raw/canonical digests, parser/chunker, metadata hash, chunk manifest, principal, authorization revision, sorted deduplicated trusted grants and expected generation. Revision identity includes source provenance and canonical digest. Generation identity hashes the payload. Exact tagged arrays are defined in `_identifiers`; V1-06 must match them with native TypeScript and cross-runtime database checks.

## Actual verification

Commands ran serially from the repository root:

```sh
uv run --project packages/python --frozen --extra postgres pytest packages/python/tests/test_ingestion.py -q
uv run --project packages/python --frozen --extra postgres mypy --config-file packages/python/pyproject.toml packages/python/src
uv run --project packages/python --frozen --extra postgres python tools/check_python_postgres.py --config /Users/vaibhavsuman/.config/cragkit/supabase/python-runtime-check.json --allow-test-writes --ingestion
uv sync --project packages/python --frozen
uv run --project packages/python --frozen pytest packages/python/tests tools/tests -q
uv run --project packages/python --frozen mypy --config-file packages/python/pyproject.toml packages/python/src
python3 tools/check_seal.py
```

Results: 37 focused cases; 327 combined Python/tool cases; strict typing across 11 source files; all 16 sealed hashes matched. Frozen default sync removed all three optional PostgreSQL packages, so the combined suite/typecheck ran without drivers. Focused failures in the peer draft were corrected: fake document/revision state, incorrect integrity-error expectations, nonidle postcommit disposal, unsafe setup error propagation and the missing write authorization boundary. Commit-error/timeout cases verify disposal without asserting an unknowable server outcome.

The final actual hosted run passed eight groups: writer LOGIN/TLS/RLS; denied same-tenant unauthorized principal with no storage change; intent replay/payload/document conflicts; canonical Unicode spans/digests/native FTS; same intent/document across two tenants; prepublication failure preserving prior generation; stale-generation CAS rejection; cancellation rollback with pool reuse. The fixture owner verified all eight application tables empty and removed its temporary policies, role and credentials. A subsequent plugin query independently confirmed zero policies/probe roles/documents/collections. Direct TLS uses certificate and hostname verification, with a private owner-only password file outside the repository. Maximum two native clients, no local database service.

E10/E11 replay/conflict and E12 prepublication interruption were exercised against PostgreSQL. This run does not establish crash recovery after a machine/process kill, two simultaneous database writer transactions, source-release authorization or TypeScript parity; those remain later scoped checks. SQLSTATE constraint classification in the shared adapter remains a separate hardening follow-up, not evidence of missing content. No live model, hosted CI, registry publication or quality evaluation occurred.
