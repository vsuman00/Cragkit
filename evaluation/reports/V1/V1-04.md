# V1-04: Canonical text and source spans

Status: COMPLETE, 21 October 2026. Both native implementations normalize text and produce matching exact UTF-8 spans.

`canonicalize` accepts scalar Unicode strings or strict UTF-8 bytes for text/plain and text/markdown. It hashes original bytes, removes exactly one leading BOM, normalizes CRLF and lone CR to LF, and preserves other content. Invalid UTF-8, surrogates, NUL, ASCII-blank input, unsupported formats and out-of-range configuration fail with `InvalidRequest`. Non-ASCII whitespace remains content; this is an explicit normalization rule.

Structural chunks preserve exact contiguous slices without gaps. Markdown recognizes basic headings and matching backtick/tilde fences; plain text does not interpret those markers. Paragraphs retain trailing space/tab-only blank lines. Oversized structures split on Unicode scalar boundaries and carry `oversized_split`; short tails can pack with following blocks, preserving the flag. IDs hash the canonical digest, byte span and explicit profile. This is basic structural parsing, not a complete Markdown renderer or extraction-truth claim.

Default source size is 1 MiB; configured source maximum is 16 MiB. Hard chunk size is 4 through 32,768 bytes, soft target defaults to 2,048 bytes, and final chunk count is at most 1,024. Byte-only paths track lengths and collect pieces without repeatedly encoding growing prefixes. Optional token mode requires a caller-owned synchronous counter, tokenizer identity and target/maximum together. It checks actual returned counts, caps calls at 65,536 and uses conservative greedy splitting without assuming monotonicity or optimality. Counter execution/determinism and external effects belong to the caller. Byte mode makes no model-token guarantee. Invalid asynchronous counters are rejected without unawaited-coroutine or unhandled-promise leakage.
