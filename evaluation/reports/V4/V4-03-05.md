# V4-03 through V4-05: bounded corrective retrieval

Local acceptance passed on 25 October 2026. This report covers the corrective engine, PostgreSQL bridge, loop termination and events. Whole-version acceptance also requires the optional adapters and final database evaluation.

## Behavior

The original query runs first. An application-approved variant can search for an unsupported required facet, while the original question, trusted scope, filters, profile and limits remain fixed. Retained candidates have a bounded union; repeated votes do not accumulate. Each retry consumes the shared ledger. Repeated normalized queries, repeated candidate sets, no progress, exhausted work and deadlines terminate the loop.

Capture reads fresh authorized source revisions before packing. Planning can take long enough for access to change, so capture runs again after planning even when its output is empty, a fallback or a repeated query. If fresh capture cannot obtain a required ranking call within budget, the engine closes admission and returns an empty assessed result with a budget limitation. It releases neither earlier evidence nor an unranked substitute. Provider failure, integrity failure, cancellation and deadline remain operational outcomes.

The PostgreSQL backend reuses caller-owned sessions and existing lexical, dense, hybrid and source boundaries. Reranking holds no database lease, then sources are freshly authorized again. This adds no migration, model runtime or pool service.

Optional event sinks queue fixed stage/count/timing fields and generated trace IDs. They omit query/source text, identities, digests, credentials and raw errors. The application explicitly flushes outside retrieval. Queues, export timeouts and concurrent exporters are bounded; late failures are observed. Draining without delivery counts as dropped. Sink failure or a full/closed queue cannot change retrieval results.
