## D-r1: bounded redacted cleanup diagnostics

Implement `tools/runtime_diagnostics.py` using the standard library only. `describe_error(error, *, operation, stage)` returns exactly operation, stage, category and sqlstate. Operation and stage use closed allowlists with `unknown` for unrecognized input. Category is one of cancelled, timeout, connection, database, validation or operation. SQLSTATE is either an exact five-character uppercase ASCII alphanumeric string or null; access to a malformed/error-raising sqlstate attribute must be safe. Do not call exception string/repr or copy exception args, diagnostics, query, DSN, resource names or arbitrary class names.

`CleanupFailure(failures, *, primary=None, stage='unknown')` takes a nonempty list/tuple of at most 16 pairs (operation, BaseException), snapshots sanitized records, and has fixed message cleanup_failed. `to_dict()` returns a detached native JSON object with exactly code=cleanup_failed, primary (sanitized operation=primary record or null) and cleanup (sanitized record list). Malformed constructor data fails with a fixed error, without interpolating input. No raw exception is retained in serialized output. Cancellation is recognized without converting it into a successful result.

Closed operations initially include primary, runtime_close, child_stop, admin_close, admin_connect, schema_restore, fixture_transaction, policy_drop, privilege_revoke, row_delete, role_drop, verify_inventory, lock_acquire, lock_release, journal_write, journal_read, journal_remove, cleanup_budget and unknown. Stages include configuration, admin_connect, lexical_fixture_locale, fixture_setup, hybrid_evaluation, dense_retrieval, vector_generations, python_ingestion, typescript_runtime, runtime_login, scope_filters, deadline_cancellation, schema_rejection, deadline_query_starting, deadline_query_observation, deadline_query_completion, deadline_query_fresh_scope_reuse, cancel_query_starting, cancel_query_observation, cancel_query_completion, cancel_query_fresh_scope_reuse, recovery and unknown.

The parent harness captures a pending original failure before cleanup. If cleanup also fails, CLI output carries the original and cleanup records separately. Successful cleanup preserves the original error/cancellation. A cleanup timeout and connection-close error must be recorded, not swallowed. Root owns parent integration, CLI regression tests, contracts and tracker. The module and independent tests have separate owners; they coordinate directly on this frozen interface.

Acceptance: classify timeout/cancellation/database failures; preserve simultaneous original and cleanup failure; reject malformed/unbounded diagnostic input; detached snapshots; secret/SQL/DSN/query canaries including malicious exception methods and sqlstate attributes. Test both module internals and CLI-visible output. No external model or database is needed for D-r1.

## R-r1: exact-ownership recovery

V4-AUD-01 follows focused D-r1 acceptance. Implement as administrative tooling only, with optional psycopg imports deferred until an explicit run. One recovery attempt uses one fresh TLS-verified administrator connection after old clients/children have been quiesced. Never reuse a cancelled/in-flight administrator connection. No change to migrations, security grants, core code or permanent database objects.

### Private ownership journal (stdlib module runtime_recovery.py)

Expose `target_fingerprint(host, port, dbname, user) -> str`, hashing a bounded native JSON identity without credentials. Expose frozen `Manifest` with serialized fields exactly version=1, run_id (16 lowercase hex), owner_nonce (64 lowercase hex), target_sha256 (64 lowercase hex), ingestion/vectors/lifecycle/allow_schema_restore (exact booleans), migration_sha256 (64 lowercase hex), vector_sha256 (64 lowercase hex or null, present iff vectors). Derive role=cragkit_probe_<run_id>, collection=probe_<run_id>, tenants=(probe_a_<run_id>,probe_b_<run_id>), policy=<role>_select and owner_marker=cragkit-runtime-v1:<owner_nonce>. Derive selected tables from the existing base fixture table list, vectors flag and migration/embedding ledgers; do not accept resource names from the journal.

`Journal.create(*, run_id, target_sha256, ingestion, vectors, lifecycle, allow_schema_restore, migration_sha256, vector_sha256, root=None)` generates owner_nonce and writes the immutable manifest before fixture mutation. Default root is ~/.config/cragkit/runtime-recovery. Leaf directory must be owned, private (0700), nonsymlink; refuse unsafe existing paths rather than chmod them. Journal filename is <run_id>.json, created exclusively, owner-only 0600, nonsymlink, single hard link, maximum 8192 bytes; fsync the file/directory. Explicit root injection is only for trusted tests. `Journal.load(run_id, *, target_sha256, root=None)` validates exact shape/types, duplicate keys, permissions/ownership, file bounds and target match before any database action. `journal.manifest` is frozen. `journal.remove()` removes only an unchanged validated journal after verified cleanup; never sweep a prefix or follow a substituted path. A mismatch fails closed. Expose `RecoveryRefused(ValueError)` with fixed safe message recovery_refused and a closed reason code for operator diagnostics (invalid_manifest, unsafe_path, target_mismatch, ownership_mismatch, unsafe_role, unexpected_policy, history_mismatch, schema_mismatch, lock_busy, fixture_remaining). Invalid/unbounded journal input never reaches SQL.

`async recover(journal, *, connect, deadline, max_attempts=2, primary=None, stage='recovery')` calls `await connect(deadline)` to obtain a transport implementing `async clean(manifest, *, deadline)` and `async close()`, with an operation label for D-r1 diagnostics. Bound all work by a finite absolute monotonic deadline, allow at most two serial attempts and no overlapping/unsettled attempts. Retry only connection failures (including SQLSTATE class 08) or explicit transaction-retry SQLSTATE 40001/40P01/55P03; ownership/config/permission failures are terminal. Observe late task exceptions and arrange closure if a cancellation-ignoring connector returns late; do not dispatch a second attempt while the first is unsettled. Keep journal on failure/timeout/cancellation. Successful recovery closes the transport, verifies cleanup and then removes the unchanged journal. Return native JSON state=passed, cleanup_verified=true, attempts, recovered flag and bounded sanitized prior failures. Terminal errors use CleanupFailure with separate original failure. Record a closed refusal reason separately when available, without copying exception content.

Missing policies/rows and an already absent role are valid on repeat only if the exact remaining inventory is empty; role absent with residual rows/policies fails closed. Verify both histories unchanged, exact rows/policies/role gone, schema canonical and advisory lock released before success. Preserve unrelated rows, policies, roles and grants.

### R-r1 integration clarifications

The recovered flag is true only after more than one attempt. Database cleanup may be repeated with an already validated manifest before journal removal; a second CLI recovery after successful journal removal fails closed without database action. A missing file is not evidence of successful prior cleanup.

Known transient restrictive policies are derived from the same exact role: _block_ready on index_generations for ingestion, _hide_profile on embedding_profiles for vectors, and _lifecycle_insert/_lifecycle_hidden on documents/document_revisions for lifecycle. Validate their expected command, permissiveness and sole role recipient before removal. Revoke only that role's privileges on known selected fixture objects. The lifecycle unknown_purge relation is deliberately outside the recovery inventory: if present, refuse schema_mismatch before mutation and retain the journal for operator inspection. Never automatically drop an unexpected relation. This is a scoped refusal boundary, not a promise to repair arbitrary schema changes.

Native integration observed PostgreSQL granting the creating administrator membership in its newly created fixture role. The fixture role must remain a member of no other role. A grant of the fixture role to the currently authenticated, configured administrator is permitted; any other inbound membership is refused. This directional exception does not grant the fixture administrative authority and does not change database permissions.
