# Scoped exact dense candidates DN-r1

V2-05 adds an internal dense method to the existing native scoped read handle. It does not change the V1 PostgresRetriever default, wire schemas or source-release policy. Hybrid orchestration and fusion remain V2-06/V2-07. No DDL, approximate index, model runtime or automatic provider call is introduced.

## Input and score

Python `await handle.dense_candidates(query_embedding, limit=100)` and Node `await handle.dense_candidates(queryEmbedding, {limit:100})` accept an E-r1 EmbeddingBatch with exactly one vector. The caller obtains it before opening the read transaction and owns text authorization/provider disclosure. The method snapshots and revalidates the complete batch before its first await. Only the provisioned FAKE_PROFILE is supported. A different valid E-r1 profile is EmbeddingProfileMismatch; unknown or malformed profile tuples fail E-r1 validation as InvalidRequest. Malformed batches, zero/multiple vectors, nonfinite/nonunit vectors or inconsistent synthetic flags are InvalidRequest; a wrong vector dimension is EmbeddingProfileMismatch. Boolean call counts, unsafe usage integers and nonfinite usage costs are rejected before SQL. No normalization, truncation or repair. Unit norm tolerance is 0.001; dimension 1536 is specific to the provisioned profile. E-r1 usage remains caller-owned; no new provider call or usage is invented by this method.

The method returns immutable DenseCandidate records with the existing lexical candidate identity/span/digest fields, score in [0,2], embedding_profile=fake_embedding_1536_v1, score_direction=lower_is_better and score_kind=cosine_distance. For example, query [1,0] ranks [1,0] at distance 0 before [0,1] at 1 and [-1,0] at 2 (actual fixtures pad with zeros to 1536). This is geometric ordering, not confidence or semantic quality. PostgreSQL stores single precision; numeric comparisons in shared synthetic acceptance allow absolute tolerance 0.000001. The [pinned pgvector 0.8.0 documentation](https://github.com/pgvector/pgvector/blob/v0.8.0/README.md#querying) defines the cosine-distance operator.

## Scope and capability

Reuse the current read-only repeatable-read transaction, trusted scope and task/context/busy/expiration guards. On dense selection, validate the canonical V2-04 vector capability, both setup hashes and exact registry tuple before executing search. Lexical-only methods keep working without vector capability. The restricted reader needs SELECT on vector/profile/setup tables and vector-schema USAGE under disclosed A-r2 managed primitive exposure. No permanent grant is installed by the library.

Canonical query: [dense_candidates.sql](../storage/postgres/queries/dense_candidates.sql). Python copies %s placeholders; Node uses numbered placeholders. Parameter order: query vector JSON, profile ID, tenant, collection, document authorization revision, grant authorization revision, principal, grant IDs, required-filter values, effective limit. Node filter placeholders start at 9. Effective limit is min(valid caller limit 1..1000, request max_candidates). All joins use full composite keys, the generation is ready and active, document untombstoned, both vector and generation profiles match, and principal/grants/revision plus required filters apply inside a materialized eligible set before distance ranking and LIMIT. No fallback to lexical or scope broadening. Ties order document/revision in C collation, ordinal, chunk ID in C collation. No index-specific approximate path is used.

Rows carry ten identity/span/digest/score fields followed by embedding and lexical profiles. Unsupported row profiles are UnsupportedCapability; malformed rows, invalid spans/scores, scope mismatch, duplicates or excess rows are IntegrityViolation. SQL/driver/deadline/cancellation errors retain existing typed operational behavior. No error becomes empty evidence.

## Sources and acceptance

DenseCandidate is accepted by the existing fetch_evidence method, revalidated and projected to the unchanged base source-candidate fields. Additional dense metadata must be validated before projection; unknown fields are rejected. Source fetching still reauthorizes current scope, grants, filters, tombstones and revision, checks exact UTF-8 spans/digests, and permits an authorized retained immutable ready generation with stale indication. Neither forged score nor profile can authorize source release.
