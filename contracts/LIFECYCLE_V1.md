# V1-09 lifecycle contract L-r1

## Policy and boundaries

Retention is caller-controlled and explicit. Live documents retain immutable ready revisions; a superseded revision can still be fetched under fresh authorization and is marked stale. No automatic expiry, background cleanup or restore API is installed. Tombstoning blocks new authorized retrieval snapshots immediately after commit; bytes already delivered cannot be recalled. Applications own backup, log and external-cache erasure and retention requirements.

A separate owner-authorized purge removes all document source content, derived generations/chunks/FTS, ingestion jobs and grants. It atomically replaces the deleted parent with a minimal tombstone (same tenant, collection, document and authorization revision; null active generation, empty metadata and original creation time). This preserves the deletion barrier against old ingestion intents. No source hashes or text are kept in this marker. The collection remains. No migrations, public wire schemas, manifests or approved corpus change.

## Internal API

Python `PostgresLifecycle(resource, authorize_lifecycle=callback)` exposes `tombstone` and `purge_tombstoned`, each with keyword collection, document_id, expected_generation_id (required nonempty identifier or None), scope and absolute monotonic deadline. Node `new PostgresLifecycle(resource, callback)` exposes the same methods with one options object, plus optional AbortSignal. The callback receives immutable scope, collection, document_id and operation (`tombstone` or `purge`) and must return exactly true. It is bound outside editable input. It runs under the deadline before acquiring a connection. Resources remain caller-owned. No I/O/driver imports at module import.

Both return immutable LifecycleReceipt: tenant_id, collection, document_id, state (`tombstoned` or `purged`), active_generation_id (string or null), changed (boolean). There is no source content in the receipt. Tombstone keeps the active pointer and metadata. Repeating a tombstone with the matching expected pointer returns changed false. Purge clears it and metadata and preserves the original creation time. Repeating purge with the matching null pointer safely repeats the atomic replacement and returns changed true (mutation performed), without claiming that data existed or that a durable purge receipt was stored. A mismatched original pointer after a lost acknowledgement remains IndexNotReady; callers must reconcile the current pointer rather than infer rollback. Tombstone still requires a matching expected pointer, including null.

Validate identities with existing ingestion scalar/UTF-8/NUL/byte bounds; parse/snapshot scope and all options before awaiting callback. Reject malformed inputs as InvalidRequest and deny callback/missing document/authorization revision mismatch as UnauthorizedScope. A mismatched active pointer is IndexNotReady. Purge of a live document is InvalidRequest. Validate stored row shape as IntegrityViolation. Recheck deadlines/cancellation after callback, queries, operation and commit. Propagate operational errors with existing fixed redacted ingestion policy; rollback errors and uncertain commits discard the connection.

## Transactions and role boundaries

Reuse the existing ingestion write transaction semantics through a small generic internal helper if needed; do not fork weaker cleanup logic. Validate catalog/history and native LOGIN/non-owner/non-superuser/non-BYPASSRLS role, bind transaction-local scope, then acquire the exact existing `cragkit.document.v1` advisory lock and lock the composite document row FOR UPDATE. All mutation predicates include tenant, collection, document, authorization revision, tombstone state and expected pointer where applicable. No grants are inferred from trusted read scope: the application lifecycle callback owns mutation authorization.

Tombstone uses the existing non-DELETE writer role guard. Purge has a distinct guard that permits DELETE on documents only and still forbids DELETE on every other Cragkit table, TRUNCATE, schema creation/ownership, elevated role membership and disabled RLS. The purge role needs SELECT on catalog/history/application tables, DELETE/INSERT on documents and column-level UPDATE(created_at) with appropriate RLS USING/WITH CHECK. The column grant permits SELECT FOR UPDATE and must be revoked explicitly when retiring or narrowing the role; table-level REVOKE alone does not remove column grants. No direct child DELETE privilege is required. Existing ingestion/read guards continue rejecting that role. No administrative resource is accepted by the library.

Before deletion, purge also validates the six expected full composite foreign key CASCADE edges, the three supported NO ACTION references, enabled internal constraint triggers and origin replication mode. When the known RLS-enabled fake vector table is provisioned, it additionally requires exactly the full composite chunk and generation/profile CASCADE edges from that table; otherwise the original nine relationships remain the expected graph. Every deleted table, including the optional vector table and lexical/grant/job leaves, is checked as a possible parent of unexpected incoming references. No vector SELECT or DELETE grant is required for the restricted parent cascade. Unexpected inbound foreign keys to deleted ancestors are unsupported because they could cascade into unrelated data. Reject an incompatible cascade catalog before mutation even if the migration ledger is unchanged.

Purge deletes exactly the locked tombstoned parent and reinserts exactly one minimal marker in the same transaction. Require one returned row at each mutation; otherwise IntegrityViolation. Use the existing ON DELETE CASCADE graph so child rows hidden by RLS cannot silently survive a successful purge. Do not disable RLS/triggers, add SECURITY DEFINER code or create a service. Verify cascades under a real restricted runtime role and a deliberately hidden child row. PostgreSQL [foreign key actions](https://www.postgresql.org/docs/17/ddl-constraints.html) and [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) govern this behavior.

The ingestion CAS already compares the caller's expected active generation while holding the same document lock. Preserve this behavior and prove a late prepared update cannot overwrite a newer commit. A failure before publication rolls back without exposing an incomplete generation. Purge does not authorize resurrection; subsequent ingest/replay for the marker remains denied by tombstone checks.
